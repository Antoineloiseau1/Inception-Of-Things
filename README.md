# 42 Project: Inception-of-Things

## Objective
This project aims to deepen your knowledge by making you use K3d and K3s with
Vagrant. You will learn how to set up a personal virtual machine with Vagrant and the
distribution of your choice. Then, you will learn how to use K3s and its Ingress.
Last but not least, you will discover K3d that will simplify your life.
These steps will get you started with Kubernetes.


NB: The whole project has to be done in a virtual machine.

This project will consist of setting up several environments under specific rules.
It is divided into three parts you have to do in the following order:
- Part 1: K3s and Vagrant
- Part 2: K3s and three simple applications
- Part 3: K3d and Argo CD

## Concepts:
### K3s:
- **Lightweight Kubernetes distribution.**
- Works with a server and agent system:
  - The K3s server acts as the control plane. It starts the Kubernetes API and maintains the cluster state.
  - The workers (K3s agents) connect to the server using a URL and a token generated by the server. Once connected, the agent registers with the API and becomes a node in the cluster. It then implements the server's decisions.

###  Vagrant :
It's a tool for creating and managing virtual machines in a reproducible way. It will create VMs based on the configurations defined in the Vagrantfiles, using VirtualBox or Docker.

### K3d

K3d is a tool that lets you run a very lightweight Kubernetes cluster locally, using Docker. K3d takes K3s and runs it in Docker containers: so instead of having actual machines or VMs, **each node in the cluster is a Docker container**.  
  
K3d does it all, we don't need Vagrant and separate VMs anymore.

When you run: `k3d cluster create` :
- Docker starts a container for the Kubernetes server (the brain)
- Docker starts one or more containers for the agents (the machines that run the applications)
- K3d automatically configures kubectl to communicate with this cluster

### CI and ArgoCD
Continuous Integration (CI) is the idea that code doesn't just live locally. With every change, something automated must check, build, and deploy.

In our setup:
- The Git repository is the source of truth.
- The Kubernetes cluster must always reflect what's in Git.

That's the role of <ins>**ArgoCD**</ins>: it's a **declarative continuous delivery tool for Kubernetes**.  
It reads YAML files (Deployments, Services, Ingress, etc.) and ensures that the actual state of the cluster matches the state described in Git.

If you modify a YAML file in Git:
- ArgoCD sees the change
- ArgoCD applies the change to the cluster
- If someone modifies the cluster manually, ArgoCD automatically fixes it

This is called GitOps: Git decides, Kubernetes executes, ArgoCD monitors.
